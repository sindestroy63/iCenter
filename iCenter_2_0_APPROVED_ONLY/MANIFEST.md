# iCenter 2.0 — MASTER MANIFEST / дизайн + функциональная спецификация

**Версия 2.0 · 16.10.2026 · предназначен для Claude Code.**

> **Приоритет:** этот MASTER MANIFEST и зафиксированные решения заказчика → утверждённые изображения из `references/` → текущая реализация (если не противоречит требованиям). Растровые картинки — визуальная цель, а не источник бизнес-правил. Не копировать ошибочные поля, статусы, данные и несуществующие функции из картинки.
>
> **Статус изображений:** в паке 12 отобранных PNG, но они НЕ все окончательно исправлены визуально. Для отсутствующих экранов не выдумывать «утверждённый дизайн». Использовать общий дизайн-системный язык и описания ниже, помечать допущения.

## A. Обязательный рабочий протокол для Claude Code

1. Сначала прочитать этот файл, `references/INDEX.md`, `README.md`; посмотреть конкретный PNG **перед реализацией соответствующей страницы**. Проверить существующие `apps/web`, `apps/api`, Prisma и реальные маршруты. Не переписывать работающие части ради архитектурной красоты.
2. Цель — визуальное соответствие по сетке, иерархии, отступам, типографике, размерам карточек, формам, теням, цветам и состояниям **в рамках реального адаптивного интерфейса**, не «похожая тема». Проверять при одинаковой ширине viewport со скриншотом; различать расхождения из-за контента и из-за CSS.
3. Каждую страницу делать вертикальным срезом: **UI → API → Prisma → реальные действия → короткая ручная проверка → скриншот сравнения**. Не создавать декоративные кнопки, которые ничего не делают. Не тратить токены на сотни искусственных тестов; проверить 1–3 критических сценария на страницу, typecheck/build и права.
4. **Никаких сбросов БД**. `icenter` (старый Payload) неприкосновенна; использовать только проверенную `icenter_v2`. Перед миграцией показывать, что меняется; существующие данные сохранять. Секреты не коммитить.
5. Отчитываться коротко: «сделано / не сделано / как проверить / ограничения». Не писать «полностью готово» по одному build. Изображения и значения из макета не являются источником достоверных цен, телефонов или наличия.
6. Если референс и описание расходятся — следовать описанию. Если два требования расходятся — не додумывать критичное бизнес-решение, задать **один** предметный вопрос. Непринципиальные UI-детали решать последовательно.
7. Не добавлять: личные кабинеты покупателей, отзывы, артикул в публичной карточке, промокоды, статусы заявок, оплату онлайн, «продано», «выручка», количественные остатки на витрине, SEO-конструктор, интеграции в настройках, публичные ссылки на сайты брендов.

## B. Визуальный контракт (общий для всех страниц)

- **Витрина:** премиальный светлый минимализм, белый фон, спокойные светло-серые подложки, тёмный текст, аккуратный синий акцент, крупные реальные изображения техники. Контент выровнен по единому max-width контейнеру; сетка карточек равномерная; пустоты и расстояния согласованы. Нет визуального шума и случайных декоративных блоков.
- **Control Panel:** фиксированная тёмная боковая навигация, светлая рабочая область, верхняя панель, таблицы/карточки, формы редактирования в правом drawer. Единый стиль заголовков, кнопок, иконок, полей, таблиц, чипов и модальных подтверждений. Drawer не должен скрывать важные действия на узких экранах.
- **Адаптивность:** desktop (1440/1280), tablet (~768), mobile (390/375). На телефоне нет горизонтальной прокрутки основной страницы; шапка и меню компактные; формы одноколоночные; длинные таблицы админки получают осмысленное мобильное представление/локальный скролл.
- **Фотографии:** `object-fit: contain` для карточек товаров и галереи; никакой обрезки iPhone/других устройств. Пропорции, фон и размер изображения стабильны между карточками. Изображения баннеров подстраиваются под слот без искажения; желательно отдельный мобильный кадр.
- **Состояния:** loading/skeleton, empty, no-results, error с retry, disabled при отсутствии допустимого действия, успех после сохранения. Любое действие должно давать обратную связь. Модальные подтверждения только для разрушительных действий.
- **Доступность:** label для полей, понятные ошибки, фокус клавиатуры, alt, управление без мыши, контраст; dropdown и drawer закрываются Esc. Не полагаться только на цвет статуса.
- **Тексты:** «Заявки» везде, не «Заказы»; «Сотрудники», не клиенты/пользователи; «В наличии» или «Под заказ · 1–2 дня»; если цены нет — «Уточнить цену». Никаких фиктивных скидок, рейтингов, отзывов, «осталось 2 шт.».
- **Дизайн-токены:** извлечь из выбранных PNG фактические цветовые/типографические/spacing пропорции и централизовать в CSS/Tailwind; не навязывать произвольные pixel-perfect числа без просмотра изображения. Повторяющиеся header, footer, sidebar, таблицы и drawer — общие компоненты.

## C. Доменная модель и бизнес-правила

### C1. Каталог и варианты
- `Brand → ProductType → Category → Subcategory → Product → Variant`; соотнести с существующей Prisma-моделью, не дублировать сущности, если уже реализованы. Подкатегория обязательна в UI там, где у выбранной категории есть дочерние разделы.
- Название продукта отдельно от вариантов. Универсальные атрибуты **выбираются по необходимости**: цвет, память, SIM, RAM, подключение Wi‑Fi/Cellular, поколение, диагональ и т.п. Диагональ, камеры, зарядка, материал, год выпуска и «особенности» не должны автоматически заполнять редактор.
- Атрибут добавляется через «+ Добавить параметр» → выбор/создание имени → добавление одного или нескольких значений → удаление с подтверждением, если используется. Список значений не означает, что существуют все декартовы комбинации; менеджер явно создаёт **реальные SKU**.
- Артикул/SKU формируется автоматически на основании названия/атрибутов при создании, не редактируется вручную, уникален и **не меняется** после переименования. Если в существующем коде есть иной механизм SKU, адаптировать без ломания ссылок.
- Изображения товара и галереи привязываются к товару/цвету (при необходимости варианту); при переключении цвета меняется галерея, память/SIM не должна без причины менять фотографию.
- Описание товара редактируется менеджером, показывается **под основной карточкой**, без отдельной перегруженной таблицы характеристик и без «Комплектации».

### C2. Города, цены, наличие
- Исходные города: Самара, Москва, Санкт-Петербург, Оренбург. Случайный `Test City` из seed не выводить на публичной витрине; не удалять автоматически из БД.
- Город определяет телефон, адрес/точки самовывоза, график работы, соцсети, часовой пояс, цены и доступность. Общих телефонов/адресов/режима работы в глобальных настройках нет. Выбор города сохраняется при переходах, используется в header/footer/контактах/карточках/корзине/checkout.
- Цена хранится на уровне `(variantId, cityId)`. Если цены нет — «Уточнить цену», не 0 и не цена Самары для Москвы. Пересчёт корзины и заявки — **на сервере** по выбранному городу; клиентская сумма не является доверенной.
- Публичное наличие: только `В наличии` либо `Под заказ` + срок поставки (типично 1–2 дня). Числовое количество на витрине отсутствует. Не путать отсутствие цены с наличием.

### C3. Заявки, персональные данные
- **Заявка**, а не классический заказ: нет жизненного цикла, статусов, «оплачено», «отправлено», «доставлено». Клиентский личный кабинет и онлайн-оплата отсутствуют.
- Заявка содержит идентификатор, дату, город, имя/телефон, предпочтительный канал связи (телефон, Telegram, MAX), способ получения (самовывоз/доставка), комментарий, список выбранных вариантов, количества и зафиксированные на момент отправки цены/сумму (или явную пометку «уточнить цену»).
- В текущей архитектуре ранее планировались Telegram lead и `OrderAttempt` без долгого хранения PII, но текущий код может содержать `/orders` и сохранение. **До реализации уточнить фактический механизм и политику хранения; не выдавать долговременное хранение заявок за согласованное без проверки.** Админский список заявок и Telegram-доставка должны согласовываться с этой моделью.
- Юридические документы и согласия: реальные ссылки на политику ПДн, условия, правила доставки/возврата (если применимо), отдельно согласие на обработку ПДн; не подставлять фиктивные реквизиты, не утверждать юридическую достаточность без проверки юристом.

### C4. Роли
- `OWNER`/`ADMIN`: доступ ко всем городам и разрешённым разделам. `CITY_MANAGER`: только назначенные города, а также отдельные флаги разрешений на цены и доступность. `DEVELOPER` (если есть): чтение, не редактирование.
- Проверять ограничения в каждом API handler/query, а не только скрывать элементы UI. Нельзя получить/изменить цену, заявку или город вне доступа через подмену ID. В интерфейсе показывать только допустимые города.

## D. Спецификация страниц публичной витрины

### D01 — Главная `/` · `references/store_home.png`
**Композиция:** общий header; крупный hero баннер; разделы каталога/брендов; «Лучшие предложения»; подборки товаров; футер с контактами выбранного города. Без входа/регистрации/ЛК, без отзывов.
**Hero:** утверждённая тема **iPhone 18 Pro / Pro Max**, не устаревший рекламный баннер; изображение/текст/CTA редактируются в слоте баннера. «Смотреть коллекцию» ведёт в реальную категорию/подборку; «Узнать больше» — в карточку или специально настроенный целевой URL. Если целевой маршрут не настроен — CTA не показывать, не вести на `#`.
**Поведение:** клик по бренду/категории открывает соответствующий список, карточка — конкретный товар, город меняет цену и контакты во всех секциях. Блок «Лучшие предложения» отображает только выбранные в админке позиции и их актуальные городские цены. Поиск в header работает.
**Приёмка:** пройти баннерные CTA, категорию, 2 товара, выбор города; проверить отсутствие ЛК и актуальность footer. Визуально сравнить hero/сетки на desktop и mobile.

### D02 — Каталог `/catalog` и брендовые разделы · `references/store_catalog_search.png`
**Композиция:** breadcrumbs, заголовок категории, фильтры, сортировка, сетка карточек, пагинация/подгрузка, empty state. Навигация бренд → тип → категория → подкатегория; не путать родительскую категорию с выбранной подкатегорией.
**Фильтры:** бренд, тип, категории, доступные характеристики (память, цвет, SIM, подключение — только релевантные), ценовой диапазон **только для товаров с известной ценой**; сортировка по цене/названию/популярности только если данные есть. URL синхронизируется с фильтрами, «Сбросить» действительно сбрасывает.
**Карточка:** полностью видимое изображение, название, вариант/«от … ₽» только если вычислено из цен текущего города, доступность, переход. Не показывать отзывы/звёзды/фиктивные скидки.
**Приёмка:** выбрать подкатегорию, фильтр, сортировку; перезагрузить страницу — фильтры сохраняются в URL; сменить город — цены корректно пересчитаны.

### D03 — Поиск `/search` + autocomplete · `references/store_catalog_search.png`
**Композиция:** поле поиска в шапке, раскрывающиеся подсказки с изображением/названием/городской ценой, отдельная страница результатов с фильтрами и пустым состоянием.
**Поведение:** debounce, отмена устаревших запросов, Enter открывает результаты, клик по подсказке открывает правильный товар, Esc закрывает список, клавиши ↑/↓ управляют выбором. Поиск по русским/английским названиям, моделям, категориям, распространённым синонимам (например, «айфон»/iPhone, «часы»/Watch); не обещать полноценный semantic AI.
**Приёмка:** «iphone», «айфон», «samsung», запрос без результатов, быстрый набор и смена города.

### D04 — Карточка товара `/product/[slug]` · `references/store_product.png`
**Композиция:** breadcrumbs, **крупная полностью видимая** основная фотография с миниатюрами слева/снизу; справа название, актуальная цена, выбор доступных атрибутов (цвет/память/SIM/подключение и т.д.), наличие/срок, количество, CTA «В корзину». **Описание товара только ниже основной карточки**, редактируется в Control Panel.
**Запрещено:** отзывы/рейтинг, публичный артикул, блок «Характеристики» в верхней зоне, блок «Комплектация», нижние декоративные меню/промо-блоки, которые не утверждены. Убедиться, что iPhone не обрезан ни на desktop, ни на mobile.
**Логика:** показывать только существующие комбинации; недоступные значения disabled или скрыты; выбор изменяет вариант, фото, цену и наличие; не подменять цену другого города. Количество — это количество единиц, добавляемых в корзину, а не остаток на складе. Не допускать заказа несуществующего SKU.
**Приёмка:** сменить цвет, память, SIM, город, количество; добавить конкретный вариант в корзину; проверить сохранение после перезагрузки и полное изображение.

### D05 — Корзина `/cart` + `CartSidebar` · отдельного финального PNG нет
**Композиция:** боковая мини-корзина после добавления и полноценная страница; позиции с миниатюрой, именем, атрибутами, ценой, количеством, удалить; итог, «Продолжить покупки», «Оформить заявку»; понятная пустая корзина.
**Логика:** хранить variantId и количество; сервер подтверждает существование варианта и цену текущего города; количество изменяется с пересчётом; при смене города пересчитываются цены/доступность, показывается уведомление о переменах. Не разрешать отправку некорректных/несуществующих вариантов; не отображать fake stock.
**Приёмка:** добавить два разных варианта, изменить количество, удалить один, сменить город, обновить страницу и перейти к checkout.

### D06 — Оформление заявки `/checkout` · `references/store_checkout.png`
**Композиция:** контакты, способ связи **Телефон / Telegram / MAX**, получение **Самовывоз / Доставка**, адрес/комментарий по необходимости, способ оплаты при получении (только реально предлагаемые варианты), справа итог и состав корзины, блок ссылок на юридические документы и отдельное согласие.
**Запрещено:** промокоды, обязательная регистрация, онлайн-оплата, несуществующие способы доставки, выдуманные реквизиты.
**Логика:** валидация телефона и способа связи, обязательных полей, адреса доставки при выбранной доставке; адрес и часы пункта самовывоза подтягиваются из города. Согласие явно отмечается пользователем; кнопка защищена от двойного отправления. Сервер повторно проверяет цены/варианты/город, создаёт заявку и/или Telegram lead согласно согласованной схеме. Ошибка доставки/сохранения не должна выглядеть как успех.
**Приёмка:** три способа связи, оба получения, отсутствие согласия, ошибка API, повторное нажатие, успешная отправка.

### D07 — Успешная заявка `/checkout/success` · отдельного финального PNG нет
**Композиция:** аккуратный экран подтверждения с номером заявки (если выдаётся), кратким составом и выбранным каналом связи, «На главную»/«Продолжить покупки». Не обещать подтверждённую покупку, оплату или статус доставки.
**Логика:** экран доступен только после подтверждённого ответа сервера; повторное открытие URL не должно создавать новую заявку; корзина очищается только после успеха. Не показывать чужие персональные данные по угадываемому URL.
**Приёмка:** успешная отправка, refresh, back, повторная отправка и отсутствие дублей.

## E. Спецификация Control Panel

### E01 — Главная `/admin` · `references/admin_dashboard.png`
**Композиция:** тёмная sidebar; сверху заголовок, период; компактные метрики **Всего заявок / Товаров / Сотрудников** (только если эти метрики действительно нужны и доступны); график **количества заявок**, последние заявки и блок **«Заявки по товарам»**.
**Последние заявки:** дата, номер, город, контакт (с соблюдением доступа), **список названий товаров текстом вместо фото**, сумма; переход в просмотр. Нет колонки статуса, действий «обработать», «отгружено».
**Запрещено:** выручка, продажи, «продано N», финансовые графики, статусы, пользователи-покупатели, создание баннера (вместо этого «Изменить баннер»), лишние виджеты из старых PNG.
**Поведение:** период влияет на график/метрики, city-manager видит только свой город, быстрые действия открывают реальные страницы.
**Приёмка:** реальные числа из БД, нулевое состояние, права менеджера, переход из последней заявки.

## F. Матрица взаимосвязей и обязательных API-сценариев

| Действие | Где меняется | Где видно | Серверная гарантия |
|---|---|---|---|
| Изменить цену SKU в Самаре | Товары → варианты → Самара | каталог, поиск, карточка, корзина, checkout | цена из `(variant,city)`; права по городу |
| Изменить цвет/галерею | Товары / Цвета / Медиа | карточка, миниатюры, корзина | существующий SKU и корректная связь media |
| Изменить контакты города | Города | header/footer, контакты, checkout | данные строго выбранного города |
| Изменить баннер | Баннеры | главная | CTA ведёт в существующий маршрут |
| Добавить в лучшие предложения | Лучшие предложения | главная | ссылка на существующий товар, нет дубля цены |
| Отправить заявку | Checkout | экран успеха, список заявок, Telegram при настроенной доставке | проверка данных/цен, идемпотентность, права доступа |
| Назначить менеджеру город | Сотрудники | доступная Control Panel | RBAC на уровне API и запросов |
| Изменить город по умолчанию | Настройки | первый визит нового покупателя | не переписывать явно выбранный город |

### API и хранение: не придумывать маршруты заранее
- Сначала найти **фактические** маршруты Fastify, Prisma models, контракт клиента и существующие `/cart`, `/orders`, `/api/v1/*`. Рефакторить названия `orders` → `requests` только осознанно, с сохранением совместимости и миграций, не ломая работающую корзину.
- Для мутаций: schema validation, auth, CSRF где требуется, city scope, запрет чужих ID, транзакция при нескольких связанных изменениях, корректные HTTP-коды, единый формат ошибок. Для публичной заявки — rate limit, защита от дублей и минимизация PII.
- Данные не подменять статическими JSON на клиенте. Если seed используется, он должен быть идемпотентным, не удалять пользователей/товары и не выдавать цены как проверенные.

## G. Короткие критерии завершения и порядок реализации

**Обязательный smoke-flow:** открыть главную → каталог → поиск → карточка → выбрать реальный SKU → добавить в корзину → сменить город → оформить заявку → увидеть подтверждение → админ видит заявку → менеджер своего города видит её, чужого нет → изменить цену/баннер/описание в админке → убедиться в обновлении витрины после перезагрузки.

**Очередность (экономия токенов):** 1) инвентаризация кода/проблем, 2) общие дизайн-компоненты и header, 3) каталог/карточка/варианты/город, 4) корзина/checkout/заявки, 5) редактор товара и цены, 6) сотрудники/RBAC, 7) контентные справочники и баннеры, 8) полировка остальных страниц и mobile. На каждом шаге — краткий результат, без переписывания всего проекта.

**Проверка визуального соответствия:** для каждой страницы открыть референс и screenshot работающего сайта при одинаковом размере окна; сравнить последовательно: (1) layout/ширина блоков, (2) шрифты/иерархия, (3) карточки/поля/кнопки, (4) цвета/тени/бордеры, (5) изображения, (6) mobile. Зафиксировать расхождения и исправить. Не обещать «pixel perfect», если макет противоречив или отсутствует.

**Критерий «готово»:** не только build, но и реально открывающаяся страница, действующие элементы, корректные данные из БД, сохранение после reload, корректная роль/город, нет критичных ошибок console/network, screenshot-сравнение.

## H. Пробелы, которые нельзя маскировать

- Нет отдельного финального PNG для корзины, success, заявок без статусов, категорий, типов товаров, городов, лучших предложений; их требования текстовые, визуальный результат нужно отдельно согласовать при необходимости.
- Юридические тексты и реквизиты не предоставлены; нельзя генерировать их как подтверждённые.
- Наличие Telegram/MAX интеграции, реальные цены других городов и политика хранения заявок должны проверяться в коде/согласовываться, не утверждать их существование по картинкам.

Самовывоз либо доставка, способы оплаты при получении, комментарий, итоговая сумма. **Убрать промокоды**. Отдельные понятные ссылки и согласия на обработку персональных данных и пользовательские условия; юридические тексты должны быть подготовлены/проверены ответственным лицом, не генерировать фиктивные реквизиты. Создание заявки через API с серверной валидацией, защита от повторной отправки, понятный результат. Не показывать статусы заказа.

## 4. Сквозные правила функциональности

1. Каждая кнопка, вкладка, поиск, фильтр, пагинация, сортировка, редактирование, сохранение и удаление должны работать; не оставлять фиктивных элементов.
2. Все изменения проходят API, серверную валидацию и сохраняются в PostgreSQL; после перезагрузки сохраняются. Ошибки показывать человеку.
3. Роли и права: OWNER/ADMIN — глобально, CITY_MANAGER — только назначенные города, DEVELOPER — только чтение, если роль существует в проекте. Детали сверить с текущей схемой и не ослаблять безопасность.
4. Цены и доступность на уровне `(вариант, город)`; отсутствие цены — «Уточнить цену», не ноль и не цена другого города. Доступность не равна числовому остатку.
5. Смена города обновляет карточки, корзину, оформление, контакты и самовывоз; менеджер не может изменять чужой город прямым API-вызовом.
6. В заявках не нужны статусы и классический order-management. Не добавлять личные кабинеты покупателей и онлайн-оплату.
7. Обеспечить корректные адаптивные экраны, клавиатурную навигацию, доступные подписи, состояния загрузки и пустых списков, отсутствие битых фото.
8. Изображения товара `contain` без обрезки. Галерея может быть общей для вариантов одного цвета, если это соответствует данным.
9. Не удалять и не сбрасывать старую БД `icenter`; работать с `icenter_v2`, проверяя фактический `DATABASE_URL`. Миграции без потери данных.
10. Демо-цифры на макетах НЕ являются данными. Если API/БД не готовы — честно обозначать демо, не выдавать фиктивную статистику за настоящую.

## 6. Что требует отдельного решения до production

- Реальные реквизиты продавца и проверенные юридические тексты: политика обработки ПДн, пользовательские условия, согласия, правила доставки/возврата, политика cookies при необходимости.
- Точная схема хранения/доставки заявок и сроки хранения PII, соответствие согласованной модели данных.
- Реальные цены, остатки/сроки, изображения и адреса каждого города; все числа на изображениях могут быть примерами.
- Отдельные страницы/скриншоты для некоторых разделов в паке представлены только частично либо обзорными коллажами; **не восстанавливать отсутствующие требования фантазией**.
